# Accessibility blocker sweep — 2026-08-22

Scope: blockers only, per the endgame audit brief. Driven against the live
console at `http://localhost:3400` with Playwright (real DOM, both
`prefers-color-scheme: dark` and `light`), not read from source. Covered
pages: work (`/`), sites (`/sites`), site-view (`/site?site_id=site-drop-the-beat`)
and its five tabs (pages, spec, history, canvas, conversation), applications,
proofs, deployments, media, components, builds, automations, settings.

The audit script lives at
`/private/tmp/claude-501/.../scratchpad/audit.cjs` (session scratchpad, not
committed) and reuses/repairs the approach in `scripts/_audit-deep.cjs`. Its
first pass reused that script's background-detection logic and produced a
large number of false positives from a real bug: it treated an element's own
*translucent* declared `background-color` (e.g. the 3–4.5% white/black glass
panels this theme uses for raised cards) as if it were fully opaque, instead
of alpha-compositing it over what's actually behind it. Fixed by walking the
full ancestor stack and compositing every layer down to white. After the
fix, contrast findings dropped from ~120 to 2 real cases (below) plus one
non-blocker (also below). A stale `scripts/_audit-report.json` in the repo
(generated before commit `74e68a04`) was not trusted for the same reason —
it reported an already-fixed dark-mode contrast issue from a `--color-text-faint`
value the current code no longer has.

## Blockers found and fixed

### 1. Keyboard-unreachable canvas edit surface (criterion 1: unreachable/unactivatable control)

- **Page / element**: site-view → Canvas tab. Every server-stamped
  `[data-fam-sel]` text leaf inside the instrumented iframe
  (`public/pages/site-view/canvas.js` loads the page; the click-to-edit
  client is `public/kit/canvas-edit.js`, injected into that iframe's own
  document).
- **What was wrong**: selection and editing were click-only. The selectable
  elements are plain text nodes (`<a>`, `<span>`, `<div>`, …) with no
  `tabindex` and `cursor: pointer` added only via CSS — they were never part
  of the tab order. A keyboard-only operator had no way to reach or activate
  the edit affordance at all; the existing `Enter`-to-edit handler required
  `selected` to already be set, which only ever happened from a `click`
  event.
- **Verified live**: tabbed into the canvas iframe with Playwright before
  the fix — `Tab` moved focus to `document.body` inside the frame and
  stopped; no `[data-fam-sel]` element ever received focus.
- **Fix** (`public/kit/canvas-edit.js`): on script init, every
  `[data-fam-sel]` element gets `tabIndex = 0` and `role="button"` (its own
  text content remains its accessible name — no `aria-label` needed). A new
  `focusin` listener selects the focused element the same way a click does
  (guarded against re-firing during `beginEdit()`'s own `el.focus()` call).
  The existing `Enter`-while-selected → edit, `Escape` → cancel, `blur`/`Enter`
  → commit logic was already correct and needed no changes.
  `public/pages/site-view/canvas.js`'s status-line copy was updated to
  mention the Tab path so the on-screen instructions match reality.
- **Verified live after fix**: `Tab` into the iframe lands on the first
  `[data-fam-sel]` element (`role="button"`, `tabindex="0"`, gets
  `.fam-selected`); `Enter` enters edit mode (`contenteditable`,
  `.fam-editing`); `Escape` cancels and restores the original text. Full
  select → edit → cancel cycle confirmed keyboard-only, no mouse.

### 2. Text contrast below 4.5:1 in nested-panel contexts (criterion 3)

Both cases are the same root cause: a color token was tuned against the
*page* background only, but the real consuming component sits inside a
raised `.card` panel (`--color-bg-raised` composited on top of
`--color-bg`), which lightens (dark theme) or muddies (light theme) the
actual backdrop just enough to drop below 4.5:1. Fixed by adjusting the
specific token, not by changing the panel/backdrop, and the honest-state
colors (`--color-ok`, `--color-warn`, `--color-error`, `--color-unknown`,
`--color-empty`) remain visually distinct from each other in both themes
after the fix (checked pairwise; only `--color-warn` needed a change).

- **Dark theme — `--color-text-faint`** (`public/app.css`). Consumers:
  `.card__meta` (work page item timestamps/footers) and `.fam-kv__key`
  (settings page path-registry keys). Measured live: 4.48:1 against
  `.card__meta`'s actual card backdrop (`rgb(18,19,23)`), 4.06:1 against
  `.fam-kv__key`'s doubly-raised `fam-section` backdrop (`rgb(28,29,33)`) —
  both below the 4.5:1 floor for this ≤12.5px, non-bold text. Old value
  `#767c92`; new value `#808697`. Re-measured against all three backdrops
  actually seen on the console: 4.65:1 / 5.13:1 / 5.53:1 — all clear 4.5:1.
- **Light theme — `--color-warn`** (`public/app.css`). Consumer:
  `.pill--warn` (work page status pills: "needs review", "informational",
  "no pages"). Measured live: 5.34:1 against the flat page background, but
  only 4.30:1 against its own tinted pill background
  (`--color-warn-bg`, 12% alpha) composited over a raised `.card` panel
  (`rgb(225,220,213)`, the backdrop it actually renders on inside a
  work-item card) — below 4.5:1. Old value `#8a5b06`; new value `#805405`.
  Re-measured: 4.83:1 against that same nested backdrop, 5.99:1 against the
  flat page background.

## Checked and found NOT to be a blocker

- **`.shell__nav-link[aria-current="page"]` border, both themes** (~1.22:1
  against its backdrop, below the 3:1 UI-boundary floor). Not fixed: this
  border is a redundant secondary cue on the "current page" nav item, which
  is already distinguished by a background-color fill
  (`--color-accent-dim`), bold weight, and a colored icon
  (`--color-accent`) — none of which rely on this border to be perceived.
  Per SC 1.4.11's intent (contrast for information the boundary is required
  to convey), a border that duplicates already-adequately-contrasted state
  is not the kind of boundary the criterion is aimed at. Left alone rather
  than weakening the panel or over-fixing a non-issue.
- **Apparent keyboard trap on the work page** — first-pass audit flagged
  `Tab` getting "stuck" on repeated `<a class="work-item__site">` links
  with identical text ("site-drop-the-beat"). Traced live: this is a false
  positive from a detector that compared tag/class/text only. The work page
  genuinely lists 41 work items that all reference the same site, so
  identical-looking `<a>` elements repeat; each `Tab` press was confirmed
  (via each list item's DOM index) to move focus to a *new*, distinct list
  item every time. No trap — just a long list of same-looking links, which
  is out of scope ("tab order that is merely suboptimal").

## Categories checked with zero findings

- **Keyboard traps**: none, after resolving the canvas issue above and the
  work-page false positive. Tabbed 60–90 elements deep on every page with no
  genuine stall.
- **Missing accessible names**: none. Checked every `button`, `a[href]`,
  `[role="button"]`, `input`, `select`, `textarea`, `[role="tab"]` across
  all 11 pages/tabs in both themes — every interactive element has visible
  text, `aria-label`, `aria-labelledby`, or `title`. Icon-only nav links
  carry visible text labels; the one `<select>` (canvas page picker) has
  `aria-label="Page to edit"`.
- **Document structure**: every page has exactly one `<h1>` and exactly one
  `<main>` landmark, in both themes. No skip link exists anywhere in the
  console, but since every page has a working `<main>` landmark, this does
  not meet the stated criterion ("a skip link that does not work") — there
  is no broken skip link, there is no skip link at all, and landmark
  navigation is available as the bypass mechanism. Not treated as a
  blocker; flagged here for visibility in case it should become one later.
- **ARIA correctness**: the tabs widget (`public/kit/tabs.js`, used by the
  site-view five-tab layout) implements the tablist/tab/tabpanel pattern
  correctly — `aria-selected` flips true/false in lockstep with the actually
  visible panel, roving `tabindex` (0 on the active tab, -1 on the rest),
  and Arrow/Home/End keyboard navigation all verified live for all five
  tabs (Pages, Spec, History, Canvas, Conversation): each activation set
  `aria-selected="true"` and moved real DOM focus onto the activated tab.
  `aria-expanded` (spec.js's raw-JSON disclosure button) was confirmed to
  toggle `"false"`/`"true"` in sync with the panel's actual visibility.
  `aria-live="polite"` regions (`public/kit/region.js`'s generic region
  loader, used by every data panel, and `spec.js`'s read view) do mutate
  their content on state changes (loading → available/empty/error), so they
  do announce; not silently inert.
