# Canonical request to Studio source association

Status: local implementation and synthetic transport proof. This associates a normal Studio-authored source with an **existing canonical agency request**, not arbitrary creation of agency customers or requests. No production activation, hosting allocation, mail, payments, external provider execution or Drive writes.

## Authority and sequence

1. The existing signed agency callback accepts `famtastic.site-studio.association-request.v1`. The real request row must match project/customer/request and current unpaid selection. The agency writer retains an immutable one-hour HMAC grant in the project. It binds the exact selected intent, selection revision/design/source, scope bytes/digest, operation and `site-studio-next` audience. It uses the existing callback authentication; no bare caller ID establishes tenancy.
2. Normal pipeline finalization retains its actual committed build result alongside the source export. A generic Studio source remains unassociated until a valid grant is consumed. Create the source once through the normal run route, then use `/api/pipeline/source/association` to obtain the grant and `/api/pipeline/source/associate` to link the existing site/run without another build. **Combined build-and-associate is unsupported:** `/api/pipeline/run` rejects an association before any work, including valid or repeated inputs. This prevents a callback failure from being mistaken for a failed build and avoids rebuilding on replay. The separate association routes require the explicitly configured staging runtime, otherwise return unavailable.
3. The association finalizer reads the stored normal run, verifies actual repository root/manifest/branch/commit/remote/clean tree and exact files, then runs the existing static browser QA. It verifies the Home bytes match the actual selected proof and binds completed content IDs only when title, description, marked heading and body equal the current authored record. Exact HTML evidence travels with those claims; the agency independently checks its hash/size and parsed fields.
4. SQLite writes one source mapping and durable callback envelope atomically. The existing runtime wake drains due pending associations before ordinary staging jobs. After restart it resends the exact envelope after byte/Git/validity checks, without another associate call or build. An acknowledgement must match association, source digest, project, customer and request. Shared project claims prevent overlap; waiting source-dependent jobs do not block unrelated projects. Each wake attempts at most eight available callbacks, skipping busy claims. Transport failures, 408 and 429 retain the exact envelope with a persisted Unix-seconds due time: exponential backoff starts at5 seconds and caps at300 seconds, without an arbitrary attempt limit while the grant remains valid. Permanent rejection, invalid acknowledgement, changed source or expired authority produces `reconciliation_required` with an actionable reason. Another identity/run/grant reusing the binding is rejected. Source origin is Studio; later handoff origin remains separate.
5. The actual signed source-finalized callback validates the stored grant and current request state, records the first mapping and invokes the normal request refresh without another Select. The first association advances one execution revision; only its exact source can retry through that automatic refresh. Changed customer input, reselection, payment and expired grants fail. Existing request edits continue through the normal writer.
6. An already complete source is packaged unchanged. A verified partial source is accepted only when its sole completion issue is `required_pages_incomplete`; the normal resolver/worker builds the missing page in the same repository. Later ancestry validation retains that original association ID/scope digest, exact wire and bound source/browser QA, plus actual Git ancestry and unchanged declared bytes. Callback or upload delay after About therefore allows only Team to build next. Partial source verification does not assert request completion. Hosting and staging receipt checks remain mandatory, and only explicit customer review acceptance can authorize checkout.

## Proven local boundary

The persistent PHP exchange harness uses real upload-free request/proof/selection/association/controller/refresh/receipt writers with synthetic Drupal persistence. Next uses a real independent Git repository, normal artifact pipeline, browser QA, durable store and synthetic protected cPanel transport. Tests cover complete Home/About transfer with one original build, Home-to-About continuation with one additional build, callback delay/restart, exact unchanged source, one repository, no preseeded source mapping, zero providers, duplicate finalization, paid/reselected/expired/cross-tenant/repository conflicts, changed bytes after QA and mismatched completed copy.

## Limits

The first association profile is static and assetless. Generated-media licensing and private-reference association need their explicit existing rights bindings; the grant is never a license. Generic sources must match the selected Home exactly and use supported requested page names/fields. External repositories outside the configured Studio source root, arbitrary app/backend work and agency customer/request creation are not claimed. Runtime and hosting target capability configuration remain installation work, not inferred from a slug or the grant. A rejected/expired pending association stays unacknowledged for reconciliation; it never authorizes a replacement identity or automatic rebuild. The proof covers kernel and agency signed controller paths; live Drupal HTTP/kernel wiring and production transport remain unproven.
